TECHNICAL SPECIFICATION – Real-Time Notification Service v2.0 | Document Status: Draft for Review | Author: Felipe Rojas (Senior Engineer) | Reviewers: Tomoko Hayashi (Architecture), Aisha Kofi (Security), Marcus Webb (Engineering Lead) | Last Updated: September 3, 2025 | 1. Overview – This document specifies the design of the Real-Time Notification Service (RTNS) v2.0, which replaces the current polling-based notification system. The current system polls the database every 10 seconds per connected client, causing O(n) database load at scale. RTNS v2.0 will use a WebSocket-based push architecture with a central message broker to deliver notifications in under 500ms P95 latency. 2. Functional Requirements – FR-01: Users must receive notifications within 500ms of the triggering event under normal load (up to 5,000 concurrent connections). FR-02: Notifications must be delivered at least once (at-least-once delivery semantics). FR-03: Users who reconnect after a disconnect must receive all missed notifications from the past 24 hours. FR-04: The system must support notification types: task assignment, mention, status change, comment, and system alert. FR-05: Notification preferences (per-user, per-type enable/disable) must be honored without additional round trips. FR-06: The service must expose a REST API for other services to publish notification events. 3. Non-Functional Requirements – NFR-01: 99.9% uptime SLA. NFR-02: Horizontal scaling without service restart. NFR-03: No notification loss during rolling deployments. NFR-04: Encryption in transit (TLS 1.2+). NFR-05: Audit logging of all published events. 4. Architecture Design – 4.1 Components: (a) Event Publisher API – REST endpoint receiving events from upstream services. Validates schema, enriches with user preference lookup, publishes to message broker. (b) Message Broker – Apache Kafka with 3-partition topic per notification type. Retention: 48 hours. Consumer group: RTNS-delivery. (c) Delivery Workers – Stateless Node.js workers consuming from Kafka. Each worker maintains a pool of WebSocket connections. Target: 1,000 connections per worker. (d) WebSocket Gateway – Load-balanced entry point for client connections. Sticky sessions via consistent hashing on user ID. (e) Preference Cache – Redis cache (TTL: 5 minutes) for user notification preferences to avoid DB hits on each event. 4.2 Data Flow: Upstream service → Event Publisher API → Kafka → Delivery Worker → WebSocket Gateway → Client. 4.3 Persistence: Notification history stored in PostgreSQL with 30-day retention. Index on (user_id, created_at DESC). 5. Open Questions – OQ-01: Should we support fallback to server-sent events (SSE) for clients that cannot maintain WebSocket connections? (Decision needed by Sep 15) OQ-02: What is the maximum acceptable notification history query window? Product team has not confirmed. OQ-03: How should we handle notification delivery when a user is logged into multiple devices simultaneously? Deliver to all sessions or most-recent only? OQ-04: Rate limiting policy for the Event Publisher API – proposed 1,000 events/second per publishing service, but this has not been validated against current event volumes. 5. Security Considerations – JWT authentication required for WebSocket handshake. Events must be scoped to the user's organization to prevent cross-tenant data leakage. Aisha to review and sign off before implementation begins. 6. Estimated Effort – Event Publisher API: 4 days. Kafka setup and schema registry: 2 days. Delivery Workers: 8 days. WebSocket Gateway integration: 3 days. Preference Cache: 2 days. Testing and hardening: 5 days. Total: 24 engineering days (2 engineers, ~2.5 weeks). Please list all open questions in this specification that must be resolved before development begins, and for each one briefly explain why it matters.

Executive Summary – The audit reviewed the end-to-end purchase-to-pay (P2P) process covering supplier onboarding, purchase order issuance, goods receipt, invoice matching, and payment authorization. The audit scope covered 1,840 purchase orders (total value €47.3M) issued in H1 2025. Overall, the control environment is partially effective. Three high-rated findings and five medium-rated findings were identified. Key themes: inadequate three-way matching controls, gaps in supplier due diligence for new vendors, and split purchase order practices to avoid authorization thresholds. | 2. Findings – Finding H1 (HIGH): Split Purchase Orders – 47 instances were identified where a single project or requirement was split across multiple POs, each below the €25,000 threshold requiring procurement manager approval. Finding H3 (HIGH): Payment Authorization Bypass – 8 payments totalling €680,000 were approved by a single authorizer without the required dual-authorization for payments above €50,000. Investigation confirmed no financial loss but represents a significant control failure. Root cause: system permission error in the ERP following a role realignment in March 2025. DATA GOVERNANCE POLICY – Version 2.1 | Effective Date: October 1, 2025 | Approved by: Data Governance Council | Document Owner: Chief Data Officer – Dr. Nadia Reinholt | 1. Purpose and Scope – This policy establishes the framework for managing data as a strategic asset across all business units. It applies to all employees, contractors, and third-party processors who create, access, modify, or delete company data. Subsidiary-specific data policies must align with this policy; in cases of conflict, this policy takes precedence. 2. Data Classification – All company data must be assigned one of four classification levels: Public (freely shareable externally), Internal (for employees only, no competitive sensitivity), Confidential (contains sensitive business, personal, or financial information; restricted distribution), Restricted (highest sensitivity; includes personal health data, M&A information, source code, and cryptographic keys; access on strict need-to-know basis). The Data Owner for each data domain is responsible for assigning and reviewing classifications annually. 3. Data Ownership – A Data Owner must be designated for every data domain in the enterprise data catalog. Data Owners are accountable for: approving access requests, ensuring classification accuracy, reviewing data quality metrics quarterly, and approving data sharing agreements. Data Stewards, assigned by Data Owners, are responsible for day-to-day data quality monitoring and metadata management. The enterprise data catalog must be updated within 10 business days of any new data domain being created. 4. Data Quality Standards – Data is considered fit for purpose if it meets five dimensions: Completeness (no required fields are null for more than 2% of records), Accuracy (validated against authoritative source systems for key entities), Timeliness (updated within the latency SLA defined per domain), Consistency (no conflicting values for the same entity across integrated systems), and Uniqueness (no duplicate primary key records). Data quality scores must be published in the data catalog monthly. Domains with a quality score below 80% must have a remediation plan within 30 days. 5. Data Retention and Deletion – Data must be retained for the periods specified in the Data Retention Schedule (Annex 1). Data past its retention date must be deleted or anonymized within 60 days of reaching end of retention. Deletion must be logged in the data catalog with the date, volume, and method. For Restricted data, deletion must be verified by the Data Owner and documented. No personal data may be retained beyond its legal basis. 6. Data Access and Sharing – Access to Confidential and Restricted data requires formal approval via the access management system. Access must be reviewed and re-certified every 6 months. Sharing data externally requires a signed Data Sharing Agreement approved by Legal and the relevant Data Owner. Data must not be exported to personal devices or non-approved storage services. 7. Compliance and Enforcement – Violations of this policy may result in disciplinary action up to and including termination. All data incidents must be reported to the Data Governance team within 24 hours of discovery. The policy will be reviewed annually by the Data Governance Council. Description of Processing – The proposed system ingests data from six internal sources to generate quarterly performance scores, attrition risk indicators, and manager effectiveness ratings. Data sources: (a) Calendar metadata (meeting frequency, response times, after-hours activity); (b) Code repository metrics (commit frequency, review participation, PR cycle time); (c) Communication platform metadata (message volume, response latency, collaboration graph); (d) HRIS data (tenure, role level, salary band, absence history); (e) Performance review history (last 3 years of ratings and comments); (f) Project management tool activity (task completion rate, overdue tasks). Outputs are used by HR Business Partners and department heads to identify employees at risk of leaving and to inform promotion decisions. | 2. Purposes and Legal Basis – Primary purpose: reduce voluntary attrition (current rate 18% in Engineering, costing an estimated €2.4M annually in recruitment and productivity loss). Necessity and Proportionality – The processing of calendar and communication metadata is potentially disproportionate. The legitimate interest of reducing attrition does not automatically justify the inference of individual work patterns from metadata at a granular level. Less intrusive alternatives not fully explored: (a) anonymous team-level retention risk indicators rather than individual scores; (b) structured stay interviews as a primary retention tool; (c) workload analytics at team level from project management data only. | 4. Risks Identified – Risk 1 (HIGH): Automated scoring of employees using communication metadata could constitute profiling with significant effects, triggering Article 22 restrictions. The vendor confirms that outputs are used as inputs to promotion decisions. Mitigation needed: exclude after-hours activity metrics from the model or apply anonymization at aggregation level. Risk 3 (MEDIUM): Data minimization principle (Article 5(1)(c)) is not met for communication metadata – message volume and response latency are not necessary for the stated attrition risk purpose. Mitigation needed: scope down to project management and HRIS data only; remove communication metadata. Risk 4 (MEDIUM): Data subject rights – employees are not informed that their data is being processed for this purpose. Privacy notice must be updated before deployment. | 5. DPO Preliminary Assessment – The DPA as currently proposed is not compliant and must not proceed to production deployment. Two HIGH risks must be mitigated before resubmission. The controller must also conduct a Legitimate Interests Assessment (LIA) documenting the balancing test against employee rights. Please evaluate the DPO's concerns, identify which of the four risks is most legally significant, and recommend the minimum set of changes the People & Culture team must make before this system can be lawfully deployed.
