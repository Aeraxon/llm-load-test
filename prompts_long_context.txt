TECHNICAL SPECIFICATION – Real-Time Notification Service v2.0 | Document Status: Draft for Review | Author: Felipe Rojas (Senior Engineer) | Reviewers: Tomoko Hayashi (Architecture), Aisha Kofi (Security), Marcus Webb (Engineering Lead) | Last Updated: September 3, 2025 | 1. Overview – This document specifies the design of the Real-Time Notification Service (RTNS) v2.0, which replaces the current polling-based notification system. The current system polls the database every 10 seconds per connected client, causing O(n) database load at scale. RTNS v2.0 will use a WebSocket-based push architecture with a central message broker to deliver notifications in under 500ms P95 latency. 2. Functional Requirements – FR-01: Users must receive notifications within 500ms of the triggering event under normal load (up to 5,000 concurrent connections). FR-02: Notifications must be delivered at least once (at-least-once delivery semantics). FR-03: Users who reconnect after a disconnect must receive all missed notifications from the past 24 hours. FR-04: The system must support notification types: task assignment, mention, status change, comment, and system alert. FR-05: Notification preferences (per-user, per-type enable/disable) must be honored without additional round trips. FR-06: The service must expose a REST API for other services to publish notification events. 3. Non-Functional Requirements – NFR-01: 99.9% uptime SLA. NFR-02: Horizontal scaling without service restart. NFR-03: No notification loss during rolling deployments. NFR-04: Encryption in transit (TLS 1.2+). NFR-05: Audit logging of all published events. 4. Architecture Design – 4.1 Components: (a) Event Publisher API – REST endpoint receiving events from upstream services. Validates schema, enriches with user preference lookup, publishes to message broker. (b) Message Broker – Apache Kafka with 3-partition topic per notification type. Retention: 48 hours. Consumer group: RTNS-delivery. (c) Delivery Workers – Stateless Node.js workers consuming from Kafka. Each worker maintains a pool of WebSocket connections. Target: 1,000 connections per worker. (d) WebSocket Gateway – Load-balanced entry point for client connections. Sticky sessions via consistent hashing on user ID. (e) Preference Cache – Redis cache (TTL: 5 minutes) for user notification preferences to avoid DB hits on each event. 4.2 Data Flow: Upstream service → Event Publisher API → Kafka → Delivery Worker → WebSocket Gateway → Client. 4.3 Persistence: Notification history stored in PostgreSQL with 30-day retention. Index on (user_id, created_at DESC). 5. Open Questions – OQ-01: Should we support fallback to server-sent events (SSE) for clients that cannot maintain WebSocket connections? (Decision needed by Sep 15) OQ-02: What is the maximum acceptable notification history query window? Product team has not confirmed. OQ-03: How should we handle notification delivery when a user is logged into multiple devices simultaneously? Deliver to all sessions or most-recent only? OQ-04: Rate limiting policy for the Event Publisher API – proposed 1,000 events/second per publishing service, but this has not been validated against current event volumes. 5. Security Considerations – JWT authentication required for WebSocket handshake. Events must be scoped to the user's organization to prevent cross-tenant data leakage. Aisha to review and sign off before implementation begins. 6. Estimated Effort – Event Publisher API: 4 days. Kafka setup and schema registry: 2 days. Delivery Workers: 8 days. WebSocket Gateway integration: 3 days. Preference Cache: 2 days. Testing and hardening: 5 days. Total: 24 engineering days (2 engineers, ~2.5 weeks). Please list all open questions in this specification that must be resolved before development begins, and for each one briefly explain why it matters.

Executive Summary – The audit reviewed the end-to-end purchase-to-pay (P2P) process covering supplier onboarding, purchase order issuance, goods receipt, invoice matching, and payment authorization. The audit scope covered 1,840 purchase orders (total value €47.3M) issued in H1 2025. Overall, the control environment is partially effective. Three high-rated findings and five medium-rated findings were identified. Key themes: inadequate three-way matching controls, gaps in supplier due diligence for new vendors, and split purchase order practices to avoid authorization thresholds. | 2. Findings – Finding H1 (HIGH): Split Purchase Orders – 47 instances were identified where a single project or requirement was split across multiple POs, each below the €25,000 threshold requiring procurement manager approval. Finding H3 (HIGH): Payment Authorization Bypass – 8 payments totalling €680,000 were approved by a single authorizer without the required dual-authorization for payments above €50,000. Investigation confirmed no financial loss but represents a significant control failure. Root cause: system permission error in the ERP following a role realignment in March 2025. DATA GOVERNANCE POLICY – Version 2.1 | Effective Date: October 1, 2025 | Approved by: Data Governance Council | Document Owner: Chief Data Officer – Dr. Nadia Reinholt | 1. Purpose and Scope – This policy establishes the framework for managing data as a strategic asset across all business units. It applies to all employees, contractors, and third-party processors who create, access, modify, or delete company data. Subsidiary-specific data policies must align with this policy; in cases of conflict, this policy takes precedence. 2. Data Classification – All company data must be assigned one of four classification levels: Public (freely shareable externally), Internal (for employees only, no competitive sensitivity), Confidential (contains sensitive business, personal, or financial information; restricted distribution), Restricted (highest sensitivity; includes personal health data, M&A information, source code, and cryptographic keys; access on strict need-to-know basis). The Data Owner for each data domain is responsible for assigning and reviewing classifications annually. 3. Data Ownership – A Data Owner must be designated for every data domain in the enterprise data catalog. Data Owners are accountable for: approving access requests, ensuring classification accuracy, reviewing data quality metrics quarterly, and approving data sharing agreements. Data Stewards, assigned by Data Owners, are responsible for day-to-day data quality monitoring and metadata management. The enterprise data catalog must be updated within 10 business days of any new data domain being created. 4. Data Quality Standards – Data is considered fit for purpose if it meets five dimensions: Completeness (no required fields are null for more than 2% of records), Accuracy (validated against authoritative source systems for key entities), Timeliness (updated within the latency SLA defined per domain), Consistency (no conflicting values for the same entity across integrated systems), and Uniqueness (no duplicate primary key records). Data quality scores must be published in the data catalog monthly. Domains with a quality score below 80% must have a remediation plan within 30 days. 5. Data Retention and Deletion – Data must be retained for the periods specified in the Data Retention Schedule (Annex 1). Data past its retention date must be deleted or anonymized within 60 days of reaching end of retention. Deletion must be logged in the data catalog with the date, volume, and method. For Restricted data, deletion must be verified by the Data Owner and documented. No personal data may be retained beyond its legal basis. 6. Data Access and Sharing – Access to Confidential and Restricted data requires formal approval via the access management system. Access must be reviewed and re-certified every 6 months. Sharing data externally requires a signed Data Sharing Agreement approved by Legal and the relevant Data Owner. Data must not be exported to personal devices or non-approved storage services. 7. Compliance and Enforcement – Violations of this policy may result in disciplinary action up to and including termination. All data incidents must be reported to the Data Governance team within 24 hours of discovery. The policy will be reviewed annually by the Data Governance Council. RFC-2025-0038: Distributed Event Sourcing with Conflict Resolution for Multi-Region Deployments | Author: Dr. Elena Vasquez, Principal Engineer | Co-Authors: James Thornton (Staff SRE), Mei-Lin Chou (Database Architect) | Status: Draft | Created: 2025-07-14 | Last Updated: 2025-09-02 | Abstract: This RFC proposes the adoption of an event-sourcing architecture with Conflict-free Replicated Data Types (CRDTs) for the Order Management Service (OMS) to enable active-active multi-region deployment across US-East, EU-West, and AP-Southeast. The current architecture uses a single-leader PostgreSQL cluster in US-East with read replicas, resulting in 180-240ms write latency for EU and AP users and a single point of failure. The proposed architecture would reduce cross-region write latency to under 15ms (local writes) while maintaining eventual consistency with a convergence window of under 500ms under normal conditions. | 1. Background and Motivation: The OMS currently processes an average of 4,200 orders per minute during peak hours, with projected growth to 8,500 orders per minute by Q2 2026 based on the expansion into 12 new markets. The single-leader architecture creates three critical problems: (a) High write latency for 62% of our user base located outside US-East, directly impacting checkout conversion rates. A/B testing conducted in June 2025 showed that each 100ms of additional latency correlates with a 1.3% drop in conversion. (b) Single point of failure: the US-East leader has experienced three unplanned failovers in the past 12 months, each causing 4-7 minutes of write unavailability. (c) Capacity ceiling: the single-leader write throughput is approaching 85% of tested maximum under current peak loads. | 2. Proposed Architecture: 2.1 Event Store Layer -- Each region maintains a local Apache Kafka cluster (3 brokers, replication factor 3) serving as the event store. Events are written locally with sub-5ms latency. Cross-region replication uses Kafka MirrorMaker 2 with a measured replication lag of 80-150ms between US-East and EU-West, and 120-200ms between US-East and AP-Southeast. 2.2 Event Schema -- All domain events use Apache Avro with a schema registry. Key event types: OrderCreated, OrderItemAdded, OrderItemRemoved, OrderPriceCalculated, PaymentInitiated, PaymentConfirmed, OrderFulfillmentStarted, OrderShipped, OrderCancelled. Each event carries a vector clock consisting of a Hybrid Logical Clock (HLC) timestamp and a region identifier. 2.3 Conflict Resolution -- Conflicts arise when the same order is modified concurrently in different regions (estimated at 0.02% of orders based on current access patterns). Resolution strategy: (a) For additive operations (item added, note appended): merge using a G-Counter CRDT; both modifications are preserved. (b) For mutually exclusive state transitions (e.g., order cancelled in EU while payment confirmed in US): Last-Writer-Wins using HLC timestamps with region ID as tiebreaker. Priority order: AP > EU > US (based on regulatory requirements for AP markets). (c) For quantity modifications: use a PN-Counter CRDT to track increments and decrements separately. 2.4 Materialized Views -- Each region maintains local materialized views rebuilt from the merged event stream. The view layer uses RocksDB for point lookups (p99 latency 2ms) and Elasticsearch for search queries. View rebuild from a full event replay takes approximately 45 minutes for current data volume (380 million events). 2.5 Snapshotting -- To bound replay time, snapshots are taken every 10,000 events per aggregate. Snapshots are stored in S3 with cross-region replication. Snapshot size per order aggregate averages 4.2KB. | 3. Data Consistency Guarantees: The system provides strong consistency within a single region (linearizable reads and writes) and eventual consistency across regions. The consistency model is formally specified as: (a) If a client writes to region R and subsequently reads from region R, the read will reflect the write (read-your-writes). (b) If a client writes to region R1 and another client reads from region R2, the read may not reflect the write for up to the convergence window (500ms p99, 200ms p50). (c) All replicas will converge to the same state given sufficient time without new writes (strong eventual consistency). | 4. Migration Strategy: Phase 1 (Weeks 1-4): Deploy event store infrastructure in all three regions. Run in shadow mode, dual-writing to both PostgreSQL and Kafka. Phase 2 (Weeks 5-8): Enable read path from materialized views for non-critical queries. Compare results with PostgreSQL reads; target 99.99% consistency. Phase 3 (Weeks 9-12): Gradually shift write traffic to event store, starting with 5% canary in EU-West. Phase 4 (Weeks 13-16): Full cutover. PostgreSQL demoted to backup/audit store with 30-day retention. | 5. Operational Concerns: 5.1 Monitoring -- Custom metrics required: cross-region replication lag (alert if >1s), conflict rate per minute (alert if >0.1%), event processing throughput per consumer group, snapshot age. 5.2 Disaster Recovery -- Region isolation capability: if a region becomes unreachable, remaining regions continue operating independently. Upon reconnection, events are replayed and conflicts resolved automatically. Tested RTO: 0 seconds (no failover needed). RPO: 0 (no data loss, events are durable locally). 5.3 Cost Estimate -- Additional infrastructure cost: $14,200/month for Kafka clusters across three regions, $3,800/month for MirrorMaker compute, $2,100/month for S3 snapshot storage, $1,900/month for additional monitoring. Total: $22,000/month ($264,000/year). Current single-region infrastructure cost: $8,400/month. Net increase: $13,600/month. 5.4 Team Expertise -- Three engineers have production Kafka experience. Two engineers have worked with event sourcing. No team members have production CRDT experience. Training plan: 2-week intensive with external consultant ($18,000) plus ongoing office hours. | 6. Alternatives Considered: 6.1 Multi-leader PostgreSQL with BDR -- Rejected because BDR conflict resolution is row-level and lacks domain-aware merge semantics. 6.2 CockroachDB -- Strong consistency across regions but write latency includes cross-region consensus round trip (150-250ms). Does not meet the sub-15ms local write latency requirement. 6.3 DynamoDB Global Tables -- Last-writer-wins only, no custom conflict resolution. Also introduces vendor lock-in with AWS. | 7. Open Questions: (a) Should we implement a conflict resolution audit log accessible to customer support? (b) What is the acceptable data staleness for the analytics pipeline? (c) Should we invest in formal verification (TLA+) of the conflict resolution logic before production deployment? Please review this RFC and identify: (1) the three most significant technical risks in the proposed architecture, (2) any gaps or unstated assumptions in the migration strategy, and (3) whether the cost justification adequately accounts for all operational expenses.
